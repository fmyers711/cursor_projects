Positioning thesis

One-line value proposition

Claroty xDome sees every medical device on the network; Splunk turns that visibility into a Clinical SOC—unified detection, investigation, and safe response without disrupting patient care.

Healthcare organizations face a dual crisis: IoMT and IoT devices proliferate faster than traditional IT security can inventory or protect them, while Clinical Engineering teams lack centralized visibility into device utilization, location, and risk. The Claroty xDome Add-on for Splunk (formerly Medigate) resolves both by funneling high-fidelity, clinically contextualized data from deep packet inspection into Splunk's centralized analytics platform.

For Splunk sellers, this is not a niche add-on—it is a platform expansion play that:

  • Extends Splunk ES and SOAR into the Clinical SOC use case—a net-new buyer (CISO + Biomedical Engineering)
  • Maps natively to CIM Vulnerabilities and the OT Security Add-On, minimizing custom field work
  • Delivers pre-packaged dashboards for security, clinical workflows, and asset management out of the box
  • Integrates with Cisco enforcement (ISE, FortiNAC) for automated, safe segmentation
  • Produces quantifiable ROI: breach prevention, capital expenditure reduction, and operational efficiency

Architecture & deployment

Medigate (Claroty xDome) acts as the network intelligence engine; Splunk acts as the analytics and incident response hub. Enforcement is handled by network security tools—not Splunk directly.

1
Capture Network TAP/SPAN or broker (e.g., Gigamon) feeds traffic to Claroty xDome for passive DPI
2
Profile xDome identifies devices (infusion pumps, MRIs, monitors), maps protocols, detects anomalies and CVEs
3
Ingest Alerts via Syslog/HEC; asset profiles via REST API polling into Splunk index
4
Analyze Splunk ES correlation, dashboards, SPL alerts; CIM-normalized for OT Security Add-On
5
Respond SOAR playbooks trigger safe isolation via Cisco ISE, Fortinet FortiNAC, or other NAC

Data ingestion methods

Customers typically combine push and pull methods to balance real-time alerting with comprehensive asset synchronization.

Method Direction Protocol / format Use case
Syslog Push TCP/UDP (port 514), CEF or JSON Real-time alerts routed through Splunk Universal/Heavy Forwarder; standard enterprise pattern
HEC Push JSON via HTTP Real-time, scalable ingestion into Splunk Cloud or Enterprise; preferred for cloud deployments
REST API Pull JSON Scheduled polling for complete asset profiles, vulnerability updates, and device state sync

Positioning tip

Syslog/HEC = security operations (alerts, anomalies, incidents). REST API = asset management and vulnerability lifecycle (inventory, CVE tracking, utilization). Both feed the same Splunk index—one platform, two buyer conversations.

CIM & OT Security Add-On mapping

Medigate's schema maps natively to Splunk's Common Information Model (CIM) Vulnerabilities data model and the OT Security Add-On. This means minimal custom field extraction and immediate compatibility with ES correlation searches, risk-based alerting, and OT Security dashboards.

Claroty / Medigate field Splunk CIM field Context

device_mac dest_mac Target device hardware address for network mapping
cisa_kev signature CISA Known Exploited Vulnerabilities catalog mapping

SPL alert examples — SE demo scripts

Pre-built searches from the add-on and community. Customize index, sourcetype, and CIDR ranges per customer environment.

External communication from medical devices

index=medigate sourcetype=medigate_iot device_category="Medical Device"
| iplocation dest_ip
| where NOT cidrmatch("10.0.0.0/8", dest_ip)
    AND NOT cidrmatch("172.16.0.0/12", dest_ip)
    AND NOT cidrmatch("192.168.0.0/16", dest_ip)
| stats count by _time, src_ip, device_name, dest_ip, dest_port, Country
| sort - count

Lateral movement / port scanning detection

index=medigate sourcetype=medigate_iot event_type="network_flow"
| bin _time span=5m
| stats dc(dest_ip) as unique_destinations, dc(dest_port) as unique_ports
    by src_ip, device_name, device_vendor
| where unique_destinations > 20 AND unique_ports > 10
| eval Alert_Trigger="Potential Lateral Movement/Scanning from Clinical Asset"
| table _time, src_ip, device_name, device_vendor, unique_destinations, unique_ports, Alert_Trigger

Legacy protocol on high-risk devices

index=medigate sourcetype=medigate_iot
| search app IN ("telnet", "ftp", "smbv1", "http")
| stats count values(app) as protocols_used by src_ip, dest_ip, device_profile, risk_score
| where risk_score > 70
| rename src_ip as Source_Asset, dest_ip as Destination

Device utilization by department (Biomedical dashboard)

index=medigate sourcetype=medigate_iot category="Infusion Pump" event_type="device_status"
| bucket _time span=1d
| stats sum(eval(if(status="Active", 1, 0))) as active_intervals
    by device_mac, device_vendor, department, location
| eval active_hours = (active_intervals * 5) / 60
| eval utilization_pct = round((active_hours / 24) * 100, 2)
| table device_mac, device_vendor, department, location, active_hours, utilization_pct
| sort - utilization_pct

Missing equipment audit

index=medigate sourcetype=medigate_iot
| stats latest(_time) as Last_Seen, latest(location) as Current_Location,
         latest(switch_ip) as Switch by device_mac, device_name
| eval Days_Missing = round((now() - Last_Seen) / 86400, 0)
| where Days_Missing > 7
| convert ctime(Last_Seen)
| table device_mac, device_name, Current_Location, Switch, Last_Seen, Days_Missing

Objection handling

Objection Response
"We already have Claroty—we don't need Splunk for this." Claroty xDome is the visibility engine; Splunk is where that data becomes actionable alongside IT security, EHR logs, identity, and cloud telemetry. The add-on exists because customers asked to unify Clinical SOC with their existing Splunk investment—not run another silo.
"IoMT security is Biomedical's problem, not the SOC." Ransomware doesn't respect org charts. Bupa Cromwell's 2024 incident started on clinical devices. The add-on gives Biomedical their dashboards and gives the SOC correlated alerts—with enforcement that Biomedical approves via allow-lists.
"We can't put agents on medical devices." Correct—and you don't. Claroty uses passive DPI via network TAP/SPAN. Zero agents, zero clinical device changes. Splunk receives metadata and alerts, not patient data.
"Our Splunk license is already strained." Scope ingestion: alerts and asset state via HEC/API are low-volume compared to raw network flow. Use summary indexing and scheduled reports for utilization dashboards. MDL tiering applies if customer is on Cisco Data Fabric.
"We need HIPAA compliance assurances." Medigate observes network metadata—device types, protocols, IPs, MACs—not PHI. Splunk access controls, role-based views, and audit logging apply. Position alongside existing HIPAA logging and retention policies.
